# Живой стенд и бот

Один VPS держит API, воркер, Postgres и кабинет: <https://bot.state3407.space>. Это демо-стенд,
а не промышленная эксплуатация — одна реплика воркера, без SLA и без контура 152-ФЗ.

Стенд нужен, чтобы проверяющий увидел работающую систему, а не только тесты. Ключ модели
проверяющему не передаётся: он живёт в `.env.prod` на хосте.

## Что стенд доказывает и чего нет

| Доказывает | Не доказывает |
|---|---|
| Код развёрнут: `/healthz` и `/readyz` отвечают `200` | Что модель, которая отвечает на стенде, измерена |
| Кабинет и admin API живые, вход по токену работает | Что демо воспроизводимо: данные на стенде свои |
| Вебхук MAX принимает событие и двигает прогон | Что бот ответит чужому аккаунту (см. ниже) |
| Загрузка документов, риски, очередь вопросов идут на реальной базе | Производительность и стоимость под нагрузкой |

Числа качества к стенду не относятся: они сняты прогонами из
[measurements](measurements/current.md) и привязаны к профилю модели. Переключать модель на
стенде ради демо не нужно — это разошлось бы с измерением.

## Что передать проверяющему

Личным каналом, не в репозитории и не в переписке с ботом:

1. адрес кабинета: <https://bot.state3407.space/admin/>;
2. токен с ролью `recruiter` из `ADMIN_TOKENS` на хосте;
3. адрес бота в MAX;
4. этот файл как чек-лист.

Роль `recruiter` показывает прогоны, риски и очередь вопросов. Она не даёт править знания и
снимать сотрудников — для проверки это лишнее право.

## Привязка аккаунта MAX

Непривязанный аккаунт получает `200` от вебхука и ничего в чате: доступ — факт компании, а не
чата ([0019](decisions/0019-a-channel-is-an-address.md)). Поэтому перед показом аккаунт
проверяющего привязывается к сотруднику.

Нужен токен HR и `external_id` — собственный id пользователя MAX, его присылает сам проверяющий
(или смотрите `unlinked_channel_user` в аудите после первого сообщения боту).

```bash
curl -X POST https://bot.state3407.space/admin/api/v1/identities \
  -H "Authorization: Bearer $HR_TOKEN" -H 'Content-Type: application/json' \
  -d '{"channel":"max","external_id":"<id проверяющего>","employee_id":"<id сотрудника>"}'
```

Ответ `204` — привязка есть, `404` — нет такого сотрудника. Нового сотрудника создаёт HR:

```bash
curl -X POST https://bot.state3407.space/admin/api/v1/employees \
  -H "Authorization: Bearer $HR_TOKEN" -H 'Content-Type: application/json' \
  -d '{"employee_id":"review-1","name":"Проверяющий","role":"Гость","department":"HR","started_at":"2026-10-25"}'
```

Идемпотентно: повторный `POST /identities` с той же парой отвечает `204`.

После привязки проверяющий пишет боту `/start` и идёт по
[manual-testing.md](runbooks/manual-testing.md). Отдельный сотрудник на каждого проверяющего
удобнее сброса: прогоны не мешают друг другу, а `demo-data-del.sql` на стенде не запускается —
он уносит корпус.

## Проверка снаружи, без доступа

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://bot.state3407.space/healthz   # 200
curl -sS -o /dev/null -w '%{http_code}\n' https://bot.state3407.space/readyz    # 200, база жива
curl -sS -o /dev/null -w '%{http_code}\n' https://bot.state3407.space/metrics   # 403 без токена
```

Если `/readyz` не `200`, база недоступна: показа не будет, это не баг кода.

## Если стенд недоступен

Стенд — одна VM. Когда он лежит, доказательство не исчезает:

- `make verify` и `make demo` поднимают тот же продукт локально и не требуют ключей;
- скриншоты кабинета лежат в `docs/assets/`;
- живой прогон MAX записан в
  [2026-10-24-live-max-and-admin](measurements/2026-10-24-live-max-and-admin.md).

Так и говорите: «стенд лежит, вот воспроизведение локально и вот протокол живой проверки».

## Ограничения, которые лучше назвать самому

- На стенде лежит закрытый корпус компании. Доступ к кабинету — это доступ к внутренним
  документам; внешнему проверяющему выдавайте роль `recruiter` и не открывайте вкладку «Знания».
- Политика хранения — `DATA_RETENTION_DAYS=365`, это заглушка до решения компании.
- Один воркер: темп отправки MAX держится в процессе, реплик больше одной не будет.

# Тизер решения

Текст для вкладки «Решение» в личном кабинете участника. Срок по сообщению организаторов —
до 10:00 (мск) 25 октября.

Шаблон организаторов: название, суть и бизнес-ценность, стек технологий, уникальность, оценка
реализации (бюджет и срок). Тест на понятность — перечитать глазами человека без ИТ-опыта: суть
и польза должны читаться без пояснений.

## Текст для отправки

```text
Название проекта: ИИ-ассистент онбординга в MAX

Суть и бизнес-ценность: ассистент адаптации нового сотрудника в корпоративном мессенджере MAX.
Ведёт новичка по сценарию от оффера до конца испытательного срока: напоминает шаги, принимает
документы, отвечает на свободные вопросы по закрытой базе знаний компании и разбирает свободные
ответы пульс-опросов. Каждый ответ — с цитатой из конкретного документа; нет цитаты или документ
не положен по роли — вопрос уходит живому рекрутёру в кабинет, а не превращается в догадку.
Рекрутёр видит прогресс, застревания и риски на одном экране вместо ручного разбора переписки
и узнаёт о проблеме до того, как сотрудник напишет заявление.

Стек технологий:
Backend: Python 3.12, FastAPI, SQLAlchemy 2, Alembic; API и воркер — разные процессы, очередь
задач и outbox в PostgreSQL: вебхук отвечает сразу, работа идёт асинхронно.
Хранение: PostgreSQL + pgvector, шифрование входящих файлов AES-GCM.
Поиск и модели: гибридный поиск (вектор + лексика + кросс-энкодер), хостинговые модели в
российском контуре, версионированные файлы промптов с прогоном оценки.
Аналитика: классификатор тональности + детерминированные правила риска.
Frontend: React 18, TypeScript, Vite, TanStack Query.
Каналы: сменные адаптеры MAX Bot API, Telegram Bot API, VK Callback API за одним контрактом.
Инфраструктура: Docker Compose, один образ на API и воркер.

Уникальность: обычный RAG-бот отвечает, пока его не поймают на галлюцинации. Здесь ответ без
проверяемой цитаты блокирует код, а не просьба в промпте: цитата обязана быть в результате
поиска по этому вопросу. База знаний фильтруется по аудитории и сроку действия до генерации,
поэтому закрытый документ не утекает в ответ. Тональность считает классификатор, а решение
о риске принимают детерминированные правила — рекрутёр видит причину, а не «модель так решила».
Каналы сменные: MAX сегодня, Telegram и VK без переписывания сценариев. Качество измерено на
137 кейсах, гейты в CI; демо поднимается одной командой без ключа модели.

Оценка реализации:
Бюджет: переменная стоимость ответа — 0.031 ₽ при хостинговом API в российском контуре
(0.0306 ₽/ответ по прайс-листу класса B). Фиксированная часть — хост, PostgreSQL, бэкапы,
мониторинг — по счёту выбранного облака: [ЗАПОЛНИТЬ: ₽/месяц]. Self-hosted GPU на L4 — 71 456
₽/месяц и окупается только выше 2 млн ответов в месяц, поэтому пилот идёт на хостинге.
Срок разработки MVP/пилота: MVP собран и проверяется автотестами и демо-набором; срок пилота
с заказчиком — [ЗАПОЛНИТЬ: недель], считая привязку аккаунтов MAX, загрузку корпуса и сверку
метрик HR.
```

## Что заполнить перед отправкой

Две ячейки в блоке «Оценка реализации» — единственные, где стоит `[ЗАПОЛНИТЬ]`. Число туда
ставится из счёта облака и плана пилота, а не из головы: выдуманный бюджет жюри проверяет
вопросом «откуда цифра», и ответа нет.

| Ячейка | Откуда взять | Почему не заполнена |
|---|---|---|
| Фиксированная стоимость, ₽/месяц | счёт российского облака: хост, PostgreSQL, объектное хранилище, бэкапы, мониторинг | В [бизнес-кейсе](business-case.md) эти строки помечены «предложение»: прайс-листа в репозитории нет |
| Срок пилота, недель | план заказчика: привязка аккаунтов MAX, загрузка корпуса, две недели логов | В брифе срока нет; выдуманная дата хуже пустой ячейки |

Переменная стоимость и цена GPU — не догадки: 0.0306 ₽/ответ и 71 456 ₽/месяц взяты из
[прайс-листа и сравнения вендоров](vendor-comparison.md) и [бизнес-кейса](business-case.md).

## Что намеренно не вошло

| Что | Почему |
|---|---|
| Числа качества (recall, цитаты, эскалация, p95) | Живут в [актуальных числах](../measurements/current.md); тизер их не переписывает, чтобы не держать цифру в двух местах |
| Названия моделей и вендоров | Жюри читает тизер, а не закупочную заявку; смена вендора не должна ломать текст |
| Скриншоты кабинета | В личный кабинет прикладывается текст, а кабинет показывается на демо |
| Обещание «до 70 % меньше рутины» | Это ожидание заказчика из брифа, а не наше измерение; в тизере нет непроверенных процентов |

## Чек-лист перед отправкой

1. Заполнить две ячейки `[ЗАПОЛНИТЬ]` по счёту облака и плану пилота.
2. Прочитать полную версию вслух: если спотыкаетесь на термине — заменить, а не объяснять.
3. Сверить числа в тексте с [актуальными числами](../measurements/current.md), если они там
   появились после правки.
4. Вставить текст в личный кабинет, вкладка «Решение», и сохранить черновик заранее: кабинет
   в последний час падает чаще, чем модель.
5. Проверить, что в тексте нет ключей, токенов, внутренних адресов и имён сотрудников.

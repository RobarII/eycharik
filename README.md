# Эйчарик
[Uploading certificate.pdf…]()

ИИ-ассистент адаптации сотрудников в мессенджере MAX: сценарии онбординга для новичков,
кабинет рекрутёра и ответы по закрытой базе знаний компании — с цитатой или эскалацией человеку.
Сделан для кейса «ИИ-ассистент в MAX» (ООО «Группа ПОЛИПЛАСТИК»).

## Локальная развёртка

Нужен Docker Compose. Для офлайн-демо `.env` не нужен: база, миграции, API, воркер и кабинет
поднимаются с детерминированным провайдером.

```bash
make review
```

Кабинет — <http://localhost:3000>, демо-токен — `dev-hr-token`. Если `make` нет:

```bash
docker compose up -d --build
docker compose run --rm api python -m onboarding.cli ingest
docker compose run --rm api python -m onboarding.cli demo --reset --yes
```

### Если нужен реальный MAX или модель

Скопируйте `.env.example` в `.env` и измените только нужные значения:

```bash
cp .env.example .env
```

| Переменная | Что поставить |
|---|---|
| `MAX_BOT_TOKEN` | токен бота из «MAX для бизнеса» |
| `MAX_WEBHOOK_SECRET` | тот же секрет, что передаёте при подписке на вебхук |
| `LLM_PROVIDER` | `openai` или `gigachat` вместо `extractive` |
| `LLM_PROFILE` | профиль из `apps/api/model-profiles/answer/` |
| `LLM_BASE_URL`, `LLM_API_KEY` | адрес и ключ выбранного провайдера |
| `EMBED_PROVIDER`, `EMBED_PROFILE` | провайдер и профиль эмбеддингов, если не локальный `hashing` |
| `ADMIN_TOKENS` | свои длинные токены вместо демо-токенов для любого публичного стенда |

Для запуска API вне Compose используйте `DATABASE_URL` с портом `55432` (его публикует
compose-проект). Для `make verify` нужна отдельная тестовая база:

```bash
docker compose exec -T postgres createdb -U onboarding onboarding_test
export ONBOARDING_TEST_DATABASE=postgresql+asyncpg://onboarding:onboarding@localhost:55432/onboarding_test
```

После изменения `.env` перезапустите стек:

```bash
docker compose up -d --build
```

Живой стенд, привязка MAX-аккаунта и ручная проверка — в [docs/live-demo.md](docs/live-demo.md).

## Проверяющему

> Один вход: **`make review`**. Поднимает стек, наполняет демо и сверяет числа через admin API.
> Кабинет — <http://localhost:3000>, токен `dev-hr-token`.

| Время | Что запустить | Что увидеть |
|---|---|---|
| 3 мин | `make review` | `verify-demo: ok`, адрес кабинета и токен |
| +5 мин | `make verify` | гейт CI: линт, типы, импорты, тесты, покрытие, доки, кабинет |
| 10 мин | [docs/checker.md](docs/checker.md) | маршрут по экранам, ожидаемый вывод, чего здесь нет |

`make verify` нужна отдельная тестовая база: без `ONBOARDING_TEST_DATABASE` он останавливается и
говорит, как её поднять. `make review` проверяет только демо-счётчики, не качество ответов: для
качества нужен `make eval` с ключом. Живой стенд без запуска — <https://bot.state3407.space>,
доступ по [инструкции](docs/live-demo.md). Ключ модели не нужен: демо отвечает детерминированным
провайдером.

## Что это сейчас

- **Вебхук MAX**: проверка секрета, дедупликация `events`, надёжная постановка задачи в очередь,
  `200` за миллисекунды.
- **Движок сценариев**: версионированный YAML, закреплённый за прогоном, кнопки, напоминания,
  опросы со шкалой на 10 баллов, эскалация по таймауту. Двадцать шагов от приветствия до конца
  испытательного срока. Ветку выбирает строка сотрудника, поэтому заводской вариант
  (`onboarding_plant`) живой, а не мёртвый контент. Приветствие спрашивает «ты» или «вы»; выбор
  хранится в прогоне и переключает текст следующих шагов.
- **Поиск**: корпус с frontmatter и JSON Schema, детерминированная нарезка, pgvector HNSW плюс
  русский `tsvector`, RRF, внешнее переранжирование, аудитория и срок как предикаты SQL. Каждый
  ответ несёт цитату из найденного набора или уходит в эскалацию.
- **Ответы**: один вызов модели, JSON-контракт, версия промпта `v7`; личные вопросы («кто мой
  наставник», зарплата, договор) уходят в эскалацию, а не получают ответ общей политикой.
- **Радар рисков**: после каждого опроса ответ классифицируется (внешняя модель с
  детерминированным запасным вариантом по совпадению слов), правила превращают сигналы в
  уровень, теги и русские причины, журнал аудита пишет `risk_assessed` / `risk_escalated`.
- **Кабинет рекрутёра**: прогоны, карточка сотрудника с хронологией аудита, очередь вопросов со
  скоупом по рекрутёру, менеджеру или HR; ответ закрывает вопрос и уходит через `outbox`; HR
  может вывести сотрудника и править документ базы знаний с проверкой frontmatter.
- **Сроки хранения и планировщик**: просроченные вопросы, загрузки, сообщения `outbox` и
  персональные поля аудита чистит воркер раз в час; политика задаётся `DATA_RETENTION_DAYS`.
  Арендованная строка `outbox` держит аренду, поэтому упавший воркер не теряет сообщение, а
  cron-точка входа делит строительные блоки с воркером.

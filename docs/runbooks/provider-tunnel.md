# Доступ к заблокированному провайдеру моделей

Измерение воспроизводимо, только если путь от этой машины до провайдера известен. Этот ранбук про
случай, когда путь — не открытый интернет: провайдер недоступен с рабочей станции, но доступен с
машины, которой мы уже владеем.

## Симптом

Каждый вызов вендора падает на транспортном уровне, до проверки любых учётных данных:

```
curl -sI https://openrouter.ai/
HTTP/2 403
```

Запрос без аутентификации на главную вендора, отвечающий `403 Access denied by security policy`, —
сетевой фильтр, а не проблема ключа. Не меняйте ключ: `GET /api/v1/key` падает так же вообще без
ключа, а тот же ключ работает с любого другого хоста.

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://openrouter.ai/api/v1/models   # 403 here
ssh vps 'curl -s -o /dev/null -w "%{http_code}\n" https://openrouter.ai/api/v1/models'  # 200 there
```

## Туннель

Один блок SSH-хоста превращает VPS в SOCKS5-прокси на loopback. Блок живёт в `~/.ssh/config`, не в
этом репозитории, потому что описывает эту рабочую станцию, а не продукт:

```
Host openrouter-tunnel
    HostName <vps-address>
    User root
    IdentityFile ~/.ssh/id_ed25519_vps_<provider>
    IdentitiesOnly yes
    DynamicForward 127.0.0.1:1080
    ControlMaster auto
    ControlPath ~/.ssh/cm-tunnel-%r@%h:%p
    ControlPersist 8h
    ServerAliveInterval 15
    ServerAliveCountMax 3
    ExitOnForwardFailure yes
```

Берите `ControlPath`, который не делит никто другой. Существующее master-соединение охотно примет
новую сессию и проигнорирует `DynamicForward`, что выглядит как мёртвый прокси при живом SSH.

```bash
ssh -f -N openrouter-tunnel
curl -s --proxy socks5h://127.0.0.1:1080 -o /dev/null -w '%{http_code}\n' \
  https://openrouter.ai/api/v1/models          # 200

ssh -S ~/.ssh/cm-tunnel-root@<vps-address>:22 -O exit openrouter-tunnel   # stop
```

`ControlPersist 8h` держит туннель живым между командами, поэтому длинному прогону оценки не нужен
собственный фоновый процесс.

## Как гонять продукт через него

`httpx` читает `HTTPS_PROXY` из окружения, когда `trust_env` включён, а это по умолчанию для
клиента, который собирает контейнер. `socks5h` резолвит имена на стороне прокси, поэтому DNS не
утекает мимо туннеля. Поддержке SOCKS нужен пакет `socksio`, он в dev-зависимостях.

```bash
HTTPS_PROXY=socks5h://127.0.0.1:1080 make eval
HTTPS_PROXY=socks5h://127.0.0.1:1080 make ingest
```

В `settings.py` ничего не меняется. Настройка прокси — свойство шелла, не продукта: деплой за
прокси выхода задаёт ту же переменную для процесса, и код знать об этом не должен.

## Что обязано быть в измерении

Отчёт, снятый через туннель, пишет это в строке окружения, потому что задержка через релей — не та
задержка, которую видит пользователь:

- пробитие `p95_latency_ms` под туннелем — не доказательство про бюджет задержки
  ([ADR 0009](../decisions/0009-latency-budget.md));
- `recall`, `leak_rate` и гейты ответа не страдают: векторы и промпт те же;
- если туннель падает в середине прогона, прогон завершается с `case_errors`, и это число должно
  быть нулём, прежде чем цитировать отчёт.

## Отказы, виденные на практике

| Симптом | Причина | Что делать |
|---|---|---|
| `Malformed reply from SOCKS server` | туннель умер между командами | перезапустить master через `-O exit`, затем `ssh -f -N` |
| `429` от бесплатного эндпоинта переранжирования | лимит на всплеск, не туннель | переранжирование повторяет с паузами 2 s и 6 s; прогон продолжается на слитом порядке, если все попытки провалились |
| `No route to host` | сам VPS лежит | подождать или взять другой хост; мёртвый релей туннель не починит |
| все вызовы снова `403` | фильтр сдвинулся или туннель обойдён | проверить, что `HTTPS_PROXY` экспортирован в том же шелле, что и команда |
